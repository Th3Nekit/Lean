# Lean 0.9.4 → 1.0.0: что изменилось и как перенести это ядро в свой клиент

> **О базовой точке.** Версии 0.9.6 в репозитории нет — последним публичным
> релизом перед 1.0.0 был **0.9.4 (`versionCode` 27)**, коммит `de6b7bc`, вершина
> ветки `awg-core`. Отсчёт здесь идёт от него.
>
> **Объём:** 94 коммита, `236 files changed, 31928 insertions(+), 3295 deletions(-)`.
>
> Документ состоит из трёх частей. **Часть I** — что поменялось. **Часть II** —
> как устроено ядро и что нужно, чтобы поставить его в другой клиент.
> **Часть III** — грабли: симптом → причина → как чинится. Третья часть на
> практике важнее первых двух: почти каждый пункт там стоил отдельного цикла
> «собрал → поставил на телефон → не работает → сутки на причину».

## Фаза 1. Миграция рантайма на NekoBox libcore

Спланирована в `77992b5` / `9b78d82` и занимает основную массу коммитов.
Суть: **отказ от прежнего рантайма в пользу libcore из NekoBoxForAndroid**

  До этого гонки старт/стоп могли оставить сервис в подвешенном состоянии.
- **Версионированные настройки, совместимые с Neko** (`2388dcc`, `ae47a7f`) —

- **Пиннинг нативного ядра** (`c4410db`, `0570799`, `c4087fc`) — воспроизводимая
  сборка из исходников по хешам (см. часть II).
- **Перевод стандартных протоколов на ядро Neko** (`e57b641`).
- **Своя служба диагностики крэшей** (`abfea87`, `12c08fb`, `d2a8473`, `d9c27ff`).
- **AmneziaWG отдельным ядром** (`b419cd4`, `ef65877`, `dbacf78`, `600d49a`) —
  и, что важно, **на TUN, которым владеет Lean**, а не на своём.
- **Живучесть рантайма** (`6e7dcff`, `ceccdc8`, `94dec77`, `301fc17`, `c827779`) —
  зависшее ядро больше не вешает подключение и не прячет собственную ошибку.
- **CI: сборка и публикация всех вариантов APK** (`0f13bcb`, `c9eeb77`, `fee4093`).
- **Аудит после миграции: 10 дефектов** (`02f3ddf`).

# Часть II. Как встроить это ядро в свой клиент

## 1. Из чего состоит «ядро»

Всё пиннится по хешам в `native/versions.lock` — это точка входа для повторной
сборки. Ничего не тянется «последним с ветки».

```jsonc
"components": {
  "neko":     { "repository": "MatsuriDayo/NekoBoxForAndroid", "revision": "5768494d…" },
  "singBox":  { "repository": "MatsuriDayo/sing-box",          "revision": "aed32ee3…" },
  "libneko":  { "repository": "MatsuriDayo/libneko",           "revision": "1c47a3af…" },
  "gomobile": { "repository": "MatsuriDayo/gomobile",          "revision": "17d6af34…" }
}
```

Тулчейн тоже зафиксирован: Go `1.23.6` для ядра, Go `1.24.4` для gomobile,
JDK 17, NDK `25.0.8775105`, `minSdk` 21, `compileSdk` 35.

Теги сборки Go — то, что определяет, какие протоколы вообще окажутся внутри:

```
with_conntrack  with_gvisor  with_quic  with_wireguard  with_utls  with_clash_api
```

ABI: `armeabi-v7a`, `arm64-v8a`, `x86`, `x86_64`.

На выходе — `libcore.aar` (gomobile-биндинг). **Важно:** локально лежащий
устаревший `app/libs/libbox.aar` способен ввести в заблуждение любой анализ
(«не компилируется»), хотя CI собирает нормально — доверять надо CI.

## 2. Второе ядро: AmneziaWG

AmneziaWG **не** живёт внутри sing-box. Это отдельный модуль `:amneziawg-core`
со своим `libwg-go.so`, собираемый из пиннутых исходников через
`native/amneziawg/build.ps1` (нужен NDK `26.1.10909125`). Из официального
Android-проекта берётся только JNI-обвязка; их сервис, UI, модель туннеля и
манифесты не копируются.

Вся поверхность — шесть методов:

```java
public interface AmneziaWgNative {
    int turnOn(String interfaceName, int tunFd, String settings);
    void turnOff(int handle);
    int getSocketV4(int handle);
    int getSocketV6(int handle);
    @Nullable String getConfig(int handle);
    String version();
}
```

**Ключевое архитектурное решение:** AWG запускается на TUN, которым владеет
приложение (`ef65877`), а не поднимает свой. Поэтому оба рантайма — sing-box и
AWG — управляются одним координатором соединения и одним `VpnService`.

Следствие, о котором легко забыть: конфиг sing-box **не должен** содержать
AmneziaWG-параметры. В `SingBoxConfig.build()` стоит явный `require`, который
отказывается собирать такой конфиг.

## 3. Что нужно реализовать на стороне клиента

libcore требует две реализации интерфейсов. В Lean это один класс
`LeanNativePlatform : BoxPlatformInterface, NB4AInterface`:

```kotlin
override fun autoDetectInterfaceControl(fd: Int)   // → VpnService.protect(fd)
override fun openTun(options: String, platformOptions: String): Long
override fun findConnectionOwner(...): Int         // ConnectivityManager.getConnectionOwnerUid
override fun packageNameByUid(uid: Int): String
override fun uidByPackageName(packageName: String): Int
override fun wifiState(): String                   // "ssid,bssid"
override fun selector_OnProxySelected(tag, selected)
override fun useProcFS(): Boolean                  // SDK_INT < Q
override fun useOfficialAssets(): Boolean
```

Плюс `LocalDNSTransport` — резолвер, работающий через `DnsResolver` активной
сети (это то, что делает значение `"local"` в настройках DNS рабочим).

Инициализация — один раз на процесс:

```kotlin
Libcore.initCore(
    processName, cacheDir, filesDir, externalAssetsDir,
    /* maxLogSizeKb = */ 2048, /* logEnable = */ true,
    platform, platform, localResolver,
)
```

Между сервисом и остальным приложением стоит слабая ссылка
(`ActiveNativeService`), чтобы колбэки ядра не держали `VpnService`:

```kotlin
interface NativeServiceBridge {
    fun openTun(tunJson: String, platformOptionsJson: String): Long
    fun protectSocket(fd: Int)
    fun currentNetwork(): Network?
    fun selectorChanged(tag: String, selected: String)
}
```

Абстракция над самим ядром намеренно узкая — её легко подменить в тестах:

```kotlin
interface NekoCore { fun newInstance(config: String): NekoBox }

interface NekoBox {
    fun setAsMain(); fun setV2rayStats(tags: String)
    fun start(); fun close()
    fun queryStats(tag: String, direction: String): Long
    fun selectOutbound(tag: String): Boolean
    fun urlTest(url: String, timeoutMs: Int): Int
    fun clearLogs()
}
```

## 4. Конфиг: схема sing-box 1.12+

Генератор (`SingBoxConfig.kt`) — **чистая функция без зависимостей от Android**,
поэтому его выход проверяется в CI настоящим `sing-box check` и запускается
`sing-box run` (smoke). Это единственный способ проверить схему без устройства и
он окупается.

Отличия 1.12 от 1.10/1.11, на которых спотыкаются при переносе:

- **DNS — типизированный формат**: `{ "type": "https" | "udp" | "local" | "fakeip", … }`.
  Порт идёт отдельным полем `server_port`, а **не** приклеенным к `server`.
  IPv6-литералы пишутся в скобках.
- **TUN** использует единый список `address`, а не `inet4_address`/`inet6_address`.
- **Перехват DNS** — через route actions (`"action": "hijack-dns"`).
- **`route.default_domain_resolver`** обязателен, если хоть один сервер задан
  именем. Без него ядро откажется стартовать.
- **WireGuard — это `endpoints`, а не `outbounds`.** Тег из общего пространства
  имён, поэтому в `urltest`/`selector`/`route.final` он подставляется как обычный
  outbound. Пустой массив `endpoints` схему ломает — не выводить его вовсе.

Стабильные теги: `proxy`, `direct`, `dns-remote`, `dns-direct`, `dns-local`,
`dns-fake`, `auto` (urltest).

## 5. Проверка серверов «URL Test»

То, ради чего чаще всего и берут такое ядро. Идея (как в самом NekoBox):
поднять **одноразовый headless-экземпляр** под один outbound и замерить
настоящий HTTP-запрос через его же handshake.

Конфиг такого экземпляра (`SingBoxConfig.buildUrlTestJson`) отличается радикально:

- **никаких `inbounds`** (ни TUN, ни mixed);
- DNS только bootstrap: единственный `dns-direct`, `final = dns-direct`, никакого
  `dns-remote` — туннеля, за которым он мог бы прятаться, ещё нет;
- `route.final = proxy`;
- **без `experimental.cache_file`** — иначе одноразовый экземпляр затрёт
  `cache.db` основного.

Дальше — `Libcore.urlTest(instance, link, timeout)`.

Ограничения, которые надо заложить сразу:

- **Стоимость.** Это поднятие ядра на каждый сервер. В Lean — семафор на 5
  одновременных экземпляров (столько же по умолчанию у NekoBox в
  `connectionTestConcurrent`).
- **WireGuard не поддерживается** — у него нет формы outbound, тест физически
  вернёт только «недоступен». Нужен явный откат на обычный TCP/UDP-пинг
  **на стороне диспетчеризации**, а не внутри пробы (см. часть III, грабля 8).
- **Блокирующие JNI-вызовы.** `start()` и `urlTest()` уходят в Go и не
  прерываются отменой корутины. Каждый вызов — на своём daemon-потоке с
  таймаутом; по таймауту поток **бросается**, а не ждётся.

# Часть III. Грабли

Каждая стоила отдельного цикла отладки. Если переносите ядро — читайте до того,
как соберёте.

### 1. `JsonNull.content == "null"` → не подключается вообще ничего

**Симптом:** ядро падает на `configure tun interface`, ни один конфиг не
подключается. Ошибка `Invalid CIDR: null`.

**Причина:** в kotlinx.serialization `JsonNull` **является** `JsonPrimitive`, и
его `content` — это строка из четырёх букв `"null"`. Поле, которое ядро законно
сериализует как null (`Inet6Address`, когда IPv6 выключен), приходит как
литеральный адрес `"null"`.

**Лечение:** отбрасывать `JsonNull` явно при разборе `TunSpec`. Ошибка летела
прямо из колбэка `OpenTun`, поэтому выглядела как «ядро не умеет в TUN».

### 2. Петля DNS: туннель поднялся и не резолвит ничего

**Симптом:** `Connected`, но ни один домен не открывается.
`dns: lookup failed for dns.google: DNS query loopback in transport[dns-remote]`

**Причина:** `dns-remote` по умолчанию — DoH на **имени** (`dns.google`), и ходит
он через прокси. Резолв этого имени заново входит в модуль DNS, ни под что не
подпадает, падает в `final` — а `final` и есть `dns-remote`.

**Лечение:** у `dns-remote` должен быть **явный** `domain_resolver`, указывающий
на `dns-direct`. `route.default_domain_resolver` этот слот **не** покрывает.
Правило `outbound: any → dns-direct` — вторая линия обороны, а не замена.

### 3. Bootstrap-DNS убивает VPN на тарифах с белыми списками

**Симптом:** на части мобильных тарифов не подключается **ни один** профиль.

**Причина:** ради паритета с NekoBox `dns-direct` был выставлен в AliDNS
(`223.5.5.5`). Этот запрос идёт по **сырой физической сети до всякого туннеля**.
На тарифе с белым списком (доступны только отдельные сервисы, остальное закрыто
до включения VPN) запрос к произвольному китайскому IP просто дропается. Имя
сервера не резолвится → `default_domain_resolver` не завершается → VPN, который
нужен именно чтобы выбраться, не может стартовать.

**Лечение:** дефолт `"local"` — резолвер платформы через `DnsResolver` активной
сети, то есть тот DNS, что выдал сам оператор. Обычный DNS такие тарифы не
режут.

**Правило шире частного случая:** всё, что дёргается **до** поднятия туннеля,
должно опираться на то, что оператор заведомо разрешает.

### 4. `protect()` и одиночный headless-экземпляр

**Симптом:** «URL Test» всегда возвращает «недоступен», когда VPN выключен —
то есть в самом частом случае.

**Причина:** `autoDetectInterfaceControl` был реализован через
`ActiveNativeService.require()`, который **бросает исключение**, если ни один
`VpnService` не установлен. Ядро зовёт этот колбэк на **каждый** исходящий
сокет — включая standalone-экземпляр, которому вообще не от чего защищаться.

**Лечение:** `currentOrNull()?.protectSocket(fd)` — безопасный no-op. Для боевого
туннеля поведение не меняется: сервис всегда установлен до старта ядра.

### 5. Пинг «сквозь» собственный туннель

**Симптом:** при включённом VPN пинги показывают RTT прокси, а не сервера.

**Причина:** `VpnService.protect()` на сыром сокете срабатывает не всегда, а
сбой проглатывался без следа.

**Лечение (принятое):** запретить сырые пробы (TCP/ICMP/GET/HEAD), пока туннель
активен, и сказать это пользователю. «URL Test» из-под запрета выведен — он
ходит через собственный экземпляр ядра и от `protect()` не зависит.

### 6. WireGuard пингуется по TCP-порту, который не может ответить

**Симптом:** все WG/AWG-серверы «недоступны», хотя рабочие.

**Причина:** WireGuard — UDP-only, TCP-порта у него нет вовсе. Проба била в TCP.

**Лечение:** WireGuard попадает в тот же класс, что Hysteria2/TUIC —
UDP-проба с откатом на ICMP.

### 7. «Холодный» первый TCP-коннект даёт фальшивые +1000 мс

**Симптом:** один и тот же сервер показывает то ~1400 мс, то ~200 мс; ручной
повторный пинг всегда «чинит».

**Причина:** часть stateful-фаерволов дропает самый первый SYN, и первое касание
платит полный таймер ретрансмиссии. Пользователь, нажимая «ещё раз», просто
прогревал путь.

**Лечение:** после успешного первого коннекта делать второй немедленно и
показывать **меньший**. Неуспешный первый не повторяется — мёртвый сервер не
оживёт, а ждать вдвое дольше на каждой мёртвой строке нельзя.

### 8. Проба, которая умеет только «недоступен», без отката

**Симптом:** после включения «URL Test» по умолчанию **все** WireGuard-серверы
стали красными.

**Причина:** диспетчеризация вызывала пробу для любого непустого outbound. Для
WireGuard проба может вернуть только `-1`. А `-1` неотличим от «сервер мёртв» —
значит, отката не происходило.

**Лечение:** решение «умеет ли проба этот outbound» должно приниматься **на
уровне диспетчеризации**, до вызова, и быть единым источником правды
(`Pinger.supportsUrlTest`, к которому делегирует `UrlTestPinger.supports`).

**Общий урок:** если функция сигнализирует об ошибке тем же значением, что и о
легитимном отрицательном результате, — вызывающий не может отличить одно от
другого. Развилку надо ставить до вызова.

### 9. Подписка схлопывается до одного сервера

**Симптом:** после обновления подписки из 20 серверов остаётся 1.

**Причина:** защита была только от **пустого** ответа. Панель на разовом сбое
отдаёт 200 OK с настоящим, но урезанным списком. `reconcile()` выдаёт ровно
столько профилей, сколько пришло, — остальные 19 удаляются по-настоящему.

**Лечение:** если количество упало более чем втрое относительно известного —
один повтор тем же UA, берётся больший результат.

### 10. Глобальный режим, который не глобальный

**Симптом:** включён «Глобальный режим», но часть трафика идёт мимо туннеля.

**Причина:** правила «российские сайты напрямую» и пользовательские rule-set'ы
продолжали работать. На сети, где прямой трафик к незанесённому адресу просто
дропается, это выглядит как «VPN не работает» именно для тех сайтов, что попали
под правило, — при статусе «Подключено».

**Лечение:** в GLOBAL глушить `ruDirect` и пользовательские rule-set'ы наравне с
`bypassLan`.

### 11. Тесты: `android.system.Os` в обычном JVM-тесте не работает

Сырые сокеты (`Os.socket`) в plain-JUnit бросают исключение, которое ловится
общим `catch` и превращается в «недоступен». Тест, который «проверяет реальный
коннект», на деле проверяет обработку исключения.

**Лечение:** выносить чистое решение в отдельную функцию и тестировать её
(`Pinger.warmResult`), а сетевую часть проверять на устройстве.

### 12. Тесты: глобальный синглтон + вечный сборщик настроек

`Http` хранит идентичность (`userAgent`, `hwid`, `sendHwid`) в глобальных
`@Volatile`-полях, а `LeanApp.onCreate()` запускает **никогда не отменяемый**
`settings.flow.collect { … }`, который их переписывает. Robolectric поднимает
настоящий `LeanApp` и делит один classloader между тест-классами — сборщик
переживает тот тест, что его запустил, и правит поля посреди чужого.

**Симптом:** тест падает дважды подряд и проходит без изменений на третий.

**Лечение:** проверять свойство, которое тест действительно заявляет (заголовки
переотправлены на втором хопе → сравнивать хоп 2 с хопом 1), а не литералы,
которыми владеет фоновый писатель.

### 13. Мелочи, стоившие времени

- **Отсутствующий `networkSecurityConfig`** убивал любую plain-http проверку.
- **Иконка уведомления**: у adaptive-icon foreground огромные безопасные поля;
  в 24dp viewport её надо перехостить, иначе глиф выглядит крошечным. И
  проверять реальный bbox — у арта Lean центр масс был на 1.7 единицы ниже
  середины, отчего значок «съезжал вниз».
- **Порядок сегментов**: `SegmentedControl` на >3 вариантах переходит на мелкий
  шрифт и обрезает подписи. Пять вариантов — уже колонка, а не строка.

## Что стоит забрать в первую очередь

Если переносите не всё, а «ядро такое»:

1. `native/versions.lock` + скрипты сборки — воспроизводимость по хешам.
2. `SingBoxConfig.kt` — чистый генератор конфига под схему 1.12 **и** его
   проверка настоящим `sing-box check`/`run` в CI. Без устройства это
   единственная реальная защита от «схема поменялась».
3. `LeanNativePlatform` + `NativeServiceBridge` + `NekoCore`/`NekoBox` — тонкий
   слой между ядром и приложением.
4. Координатор соединения с «побеждает последний запрос» и **ограниченными по
   времени** нативными вызовами.
5. Часть III целиком.
